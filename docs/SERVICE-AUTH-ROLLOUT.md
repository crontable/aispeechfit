# 카카오 서비스 로그인과 데이터 연결

## 구현 상태

### 운영 DB 적용 현황

2026-09-13 사용자가 가져온 키를 STANDBY 상태로 등록한 뒤 실제 Data API 서명 수용을 확인했다. Rotate keys는 실행하지 않았다. `auth-schema:cutover --apply`로 이용권·접근 정책 전환을 커밋했다. 새 서비스 이용권 1건, 비공개 원본 이용권 31건, 기존 인증 계정 56개를 확인했고 본인 이용권의 기간·상태·생성 및 수정 시각 보존을 확인했다. 실제 Data API에서 본인 이용권 허용, 존재하지 않는 세션 거부, 학습 자료 조회가 통과했다. localhost 브라우저에서도 학습 목록과 기능해부학 챕터 문제 화면이 열렸다.

운영 DB의 서비스 접근은 이제 Better Auth 세션을 기준으로 한다. 기존 Supabase 인증만 사용하는 배포본으로는 학습 접근이 되지 않으므로 다음 필수 단계는 운영 웹 환경 변수 반영과 새 코드 배포다. 현재 검증은 localhost 코드와 운영 DB의 조합이며, 운영 도메인·운영 카카오 앱·모바일 실기기 검증은 미완료다. 아래 키 미등록·이용권 미적용 설명은 전환 전 준비 기록이다.

2026-09-13 운영 DB에 신규 `better_auth` 테이블 6개와 제한된 역할 `better_auth_runtime`, `better_auth_phone_writer`를 실제 적용했다. localhost의 개발 앱 로그인으로 운영 인증 DB에 사용자 1명·유효 세션 1개·전화번호 확인 1건을 생성하고 확인했다. 기존 Supabase 인증 사용자·이용권·학습 접근 정책은 변경하지 않았다. 아래의 원격 스키마 미생성 기록은 이 적용 전 조사 결과다.

인증 역할은 기본 인증 테이블을 관리하고 전화번호 확인 테이블은 읽기만 가능하다. 검증 역할은 카카오 확인 테이블을 쓰고 세션·계정은 조회한다. 세션 행 잠금에 필요한 UPDATE 권한과 USING 정책을 주되 WITH CHECK false로 실제 세션 변경을 거부한다. 운영 DB에서 인증 역할의 전화번호 변경과 검증 역할의 세션 변경이 모두 42501로 거부됨을 확인했다. 계정 비밀번호는 무작위 생성하여 무시되는 환경 파일에만 저장했고 DB 소유자 자격을 앱 실행에 사용하지 않는다.

`KAKAO_REMOTE_AUTH_TEST_ENABLED=true`는 NODE_ENV=development일 때만 로컬 테스트 DB 대신 원격 역할을 사용하고 http://localhost:3000 callback을 허용한다. 운영 웹 배포에서는 HTTPS BETTER_AUTH_URL이 필요하다. 원격 DB 검증 성공과 운영 웹사이트 배포 완료는 구분한다.

`pnpm auth-schema:preflight`는 공개 키 발견, 실제 원격 앱·카카오 subject와 확인 세션의 일치, Data API 서명 수용을 확인한다. 현재 실행은 SIGNING_KEY_NOT_REGISTERED에서 중단되어 이용권 전환은 미적용이다. 가져오기용 개인 JWK는 `.env.supabase-signing-key.local`에 준비되어 있으며 Git에 포함하지 않는다.

키 등록 후 `pnpm auth-schema:cutover`가 원본 후보의 해시를 다시 대조하고 접근 정책과 선택 이용권 전환을 단일 트랜잭션으로 적용한다. 성공 후 실제 Data API에서 본인 이용권 허용·존재하지 않는 세션 차단·학습 자료 조회를 확인한 경우에만 로컬 BETTER_AUTH_DATA_API_READY를 활성화한다. 커밋 후 검증 실패는 committed=true로 보고하며 재실행으로 덮어쓰지 않는다. 운영 웹 배포 설정에도 역할 URL·인증 secret·앱 키·서명 키·HTTPS origin을 반영해야 한다.

2026-09-13 원본 읽기 전용 조사를 완료했다. 인증 계정 56개, 이용권 31개(소유자 31명), 현재 유효 이용권 2개, 고아 참조 0개다. 이 건수는 실사용자 수를 뜻하지 않는다. 사용자가 지정한 기존 계정은 단일 계정이며 이용권 1개가 현재 유효하다. 조사 당시 원격 `better_auth` 스키마는 없었으며, 이후 위 운영 DB 적용을 완료했다. 서비스에서 `auth.users`를 참조하는 FK는 `public.tickets.fk_user`이며 `ON DELETE CASCADE`다. 이용권을 참조하는 다른 테이블과 사용자 정의 트리거는 없다. 현재 4개 서비스 테이블의 RLS·정책·권한은 #26 구성과 일치한다.

본인 이용권 한 건을 로컬 `auth_source.ticket_transfer_candidates`에 준비했다. 원본 JSON 텍스트와 SHA-256, 전화번호 확인을 마친 단일 개발 카카오 사용자 참조를 보관했다. 이메일과 원본 인증 사용자 전체는 복사하지 않았다. 이 후보는 실제 이용권 발급이나 원격 소유권 변경이 아니다. 원격 인증 사용자가 준비되면 동일 앱·카카오 subject를 다시 확인하여 목적지를 확정해야 한다. 로컬 사용자 UUID를 원격에 존재한다고 가정하지 않는다.

`AUTH_TICKET_SOURCE_EMAIL`을 실행 환경으로 전달해 `pnpm auth-migration:prepare-ticket`를 실행한다. 원본은 읽기 전용, 목적지는 기존 로컬 DB 주소로 제한한다. 계정·현재 유효 이용권·확인된 카카오 대상이 단일하지 않으면 중단한다. 같은 후보는 재실행해도 중복 생성하지 않으며, 원본 값이나 연결 대상이 바뀌면 덮어쓰지 않고 검토를 요구한다. 후보 테이블은 일반 API 역할에 공개하지 않는다.

전환 대상은 사용자가 지정한 현재 유효 이용권 한 건이다. 만료·비활성 이용권은 후보 선정과 사용자 매핑에서 제외한다. 다른 유효 이용권도 자동 매핑하지 않는다. 기존 기록은 비공개 `auth_source.tickets`에 원래 행 그대로 보관하고, 새 `public.tickets.user_id`는 `better_auth.users.id`를 참조한다. 전체 인증 사용자 이관이나 만료 이용권 매핑은 선행 조건이 아니다.

`20260913020000_transfer_selected_ticket.sql`은 기존 테이블을 보관 스키마로 이동하고, 새 서비스 테이블에 지정한 유효 이용권 한 건만 복사한다. 원본 ID·기간·상태·생성 및 수정 시각은 유지하고 소유자만 확인된 새 사용자로 연결한다. 보관 행은 일반 API에서 읽을 수 없다. 새 이용권의 사용자 삭제 정책은 RESTRICT이며 기존 이용권은 기존 소유자 참조를 유지한다. 기존 인증 사용자 삭제는 이 전환에 포함하지 않는다.

전환 SQL에는 `app.ticket_source_id`, `app.ticket_target_user_id`, `app.kakao_app_id`를 동일 DB 연결의 설정으로 전달한다. 실제 원격 카카오 사용자 검증 후 값을 확정한다. 새 인증 스키마와 세션 접근 함수가 먼저 있어야 한다. 원격 배포 도구는 각 파일의 BEGIN/COMMIT 경계를 정리하여 정책·이용권 전환을 하나의 트랜잭션으로 적용해야 하며, 운영 역할과 서명 키 검증 전 개별 적용하지 않는다. 현재 전환 도구까지 구현했으며, 서명 키 등록과 이용권·접근 정책의 원격 적용은 미완료다.

같은 이름의 복구 SQL은 새 이용권이 원래 한 건 그대로일 때에만 새 테이블을 제거하고 기존 테이블을 되돌린다. 새 이용권 발급이나 기간·상태 변경이 있으면 중단하여 운영 데이터를 지우지 않는다. 복구 순서는 이용권 전환 복구 → 세션 접근 정책 복구다.

로그인 화면의 Google 버튼·인앱 브라우저 경고를 제거하고 Better Auth 카카오 로그인을 연결했다. `/auth/complete`에서 현재 세션의 전화번호를 자동 확인하고 `/study`로 이동한다. `/study` 레이아웃과 챕터 페이지는 각각 서버에서 세션·전화번호 확인·이용권을 검사한다. `/unauthorized`도 서버가 이용권을 조회하며 조회 실패와 이용권 부재를 구분한다. 로그아웃은 Better Auth 세션을 종료한다. 구 `/auth/callback`은 Supabase 세션 교환 없이 로그인 화면으로 돌려보낸다.

현재 localhost 서비스는 개발 앱과 운영 DB의 `better_auth` 테이블을 사용한다. 서비스 화면에서 실제 카카오 로그인 → 전화번호 자동 확인 → 이용권 조회 불가 안내까지 확인했다. 실제 Supabase Data API 연결 설정과 본인 이용권 연결은 아직 완료하지 않았다. 이 상태에서 조회 불가 안내를 이용권이 없다는 증거로 사용하지 않는다.

## 데이터 연결 구성

`lib/data/token.ts`는 검증된 세션의 사용자 UUID와 session ID를 담은 ES256 토큰을 만든다. 수명은 최대 60초이며 세션 만료를 넘기지 않는다. `lib/data/client.ts`는 서버에서만 토큰을 전달한다. 세션과 사용자가 다르거나 만료되면 토큰을 만들지 않는다. 비밀키·토큰·전화번호 원문은 브라우저로 전달하지 않는다.

`supabase/migrations/20260913010000_connect_better_auth_access.sql`은 기존 #26 정책에 새 세션 조건을 AND로 추가하는 restrictive 정책을 적용한다. 이용권은 유효한 새 세션의 본인 행만 보이고, 학습 자료는 현재 전화번호 확인 버전과 이용권 조건까지 만족해야 한다. 보조 함수는 현재 요청에 대한 boolean만 반환하며 고정 search_path로 인증 테이블을 읽는다. 기존 공개 정책을 무조건 삭제하지 않는다.

이 접근 정책 SQL은 기존 tickets 행이나 FK를 변경하지 않는다. 이용권 한 건의 연결은 별도 `20260913020000_transfer_selected_ticket.sql`이 담당한다. 함께 둔 복원 SQL은 기존 #26 정의로 돌아가는 전환 전 복구용이며, 운영에 적용하기 전 실제 정의를 기록하고 비교해야 한다.

## 운영 연결 전 준비

1. 원본 SQL 접속으로 실제 테이블·FK·정책·역할을 읽기 전용으로 확인한다. 전체 사용자 이관은 수행하지 않는다. `.env.local`의 `SUPABASE_MIGRATION_SOURCE_DATABASE_URL`은 이 조사에 사용할 수 있다.
2. 같은 검증용 Supabase 프로젝트 안에 인증 스키마와 서비스 테이블을 준비한다. 현재 로컬 인증 DB와 원격 서비스 DB를 조합한 상태에서는 원격 정책이 로컬 세션을 읽을 수 없으므로 접근 완료로 간주하지 않는다.
3. 인증 실행 역할과 전화번호 쓰기 권한을 구성하고 `AUTH_DATABASE_URL`을 설정한다. 현재 로컬의 DB 소유자 접속을 운영 자격으로 사용하지 않는다. 운영 역할·별도 쓰기 자격은 구성 및 검증을 완료했다.
4. Supabase에 가져온 ES256 서명 키의 개인 JWK와 kid를 서버의 `SUPABASE_DATA_SIGNING_JWK`에 설정한다. 원격 Data API가 실제 서명을 수용하는지 검증한다. 일반 조회에 service_role 키를 사용하지 않는다.
5. 기존 정책 기록과 복구 준비 후 새 정책을 적용하고 직접 Data API 테스트를 수행한다. 본인 이용권 참조를 새 사용자로 연결한다. 로컬 정책 검사 통과를 원격 Data API 검증으로 대체하지 않는다.
6. 위 조건이 맞는 배포 환경에서만 `BETTER_AUTH_DATA_API_READY=true`로 설정한다. 값이 없거나 false면 앱은 데이터 조회를 시도하지 않고 조회 불가 상태를 표시한다.
7. `BETTER_AUTH_URL`의 HTTPS 주소와 카카오 callback `/api/auth/callback/kakao`를 맞춘다. 실제 서비스 설정을 시험할 때 로컬 검증 우선 설정인 `KAKAO_AUTH_TEST_ENABLED`를 해제한다. 운영에서는 이 개발 플래그가 무시된다.
8. 실제 모바일 카카오톡에서 로그인·복귀·학습 접근을 확인한 뒤 배포한다.

## 검증 범위

### 원본 연결 점검

Session pooler와 공식 CA를 사용한 TLS 검증을 구성한 후 비밀번호 인증 문제가 해결되어 원본 조사를 완료했다. 아래 Direct connection 실패 기록은 해결 전 경과다.

`pnpm auth-migration:inspect`는 TLS 인증서 검증을 사용하고, `REPEATABLE READ READ ONLY` 트랜잭션에서 이용권 열·외래 키·정책·권한과 집계 건수만 조회한다. 사용자 행, 인증 토큰, 전화번호, 접속 문자열을 출력하거나 복제하지 않는다. RLS로 일부 행만 보이는 집계를 전체 건수로 오인하지 않도록 `row_security = off`를 설정하고 권한이 부족하면 실패한다.

2026-09-13 원본 접속 설정이 입력된 뒤, Direct connection 호스트가 현재 서비스 프로젝트와 일치함을 확인했다. DNS에는 IPv6 주소만 있었고 현재 실행 환경의 연결은 `ENOTFOUND`로 실패했다. DB 조회는 수행되지 않았다. Connect → Method → Session pooler에서 제공되는 호스트(`…pooler.supabase.com`)와 포트 `5432`를 사용하는 연결 문자열로 교체해야 한다. 사용자 이름도 제공된 문자열을 그대로 사용하고 DB 비밀번호를 채운다. 원본 조사 전까지 실제 이용권 건수·FK·정책은 미확인 상태다.

`pnpm test:service-auth`는 ES256 서명·만료·사용자 결합, Google 요청/외부 Origin/보호 필드 차단, 실제 PostgreSQL에서 새 UUID·타인 이용권·구 발급자·전화번호 버전·이용권 만료/비활성·삭제 세션을 검사한다. 임시 DB에 실제 #26 정책과 새 SQL을 적용하고 합성 자료를 조회한다. 선택한 이용권 한 건의 전환, 만료 대상 거부, 다른 유효·만료·비활성 행의 원본 보존, 보관 테이블 접근 차단, 변경된 이용권의 복구 거부와 원본 복구까지 포함해 부모 검사 포함 9개이며 HTTP Data API 자체의 서명 검증은 후속이다.

공식 근거는 [Supabase 외부 JWT](https://supabase.com/docs/guides/auth/jwts), [서명 키 가져오기](https://supabase.com/docs/guides/auth/signing-keys)다.
